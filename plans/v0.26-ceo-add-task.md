# v0.26 — dynamic replanning (step 1): the CEO can add tasks mid-run — self-built

The first step of Priority-1 dynamic replanning: give the CEO a new **`add_task`** action so it can
**extend the DAG during a run** when execution reveals work the plan was missing. This is the foundational
"create" case; split/replace/invalidate are follow-ups, and this is what unblocks a future repair→replan.
Feasible because `runtime.addTask` is event-sourced with no "already started" guard — adding a task mid-run
just appends `task.added` and the Kahn waves recompute.

## Changes — `@flow/ceo`
- `types.ts`: `CeoAction` and `CEO_ACTIONS` gain `"add_task"`. New `NewTask` interface
  `{ id, role, tier, deps?, instruction, verify? }`. `CeoDecision` gains `newTasks: NewTask[]` (empty for
  every non-add_task action, mirroring `taskIds`).
- `parse.ts`: parse `newTasks` (array; each needs a non-empty `id` and `instruction`; `role`/`tier` default to
  backend/sonnet; `deps`/`verify` optional). Defaults to `[]`.
- `prompt.ts`: the system prompt documents `add_task` ("extend the plan with NEW tasks when execution revealed
  missing work; put them in `newTasks`") and the reply schema includes `newTasks`.
- `test/add-task.test.ts` (new): `parseDecision` reads an `add_task` decision with `newTasks` (deps/verify
  preserved, defaults applied); `newTasks` defaults to `[]` for other actions.

## Changes — `@flow/orchestrator`
- `orchestrator.ts`: handle `decision.action === "add_task"` — for each `newTasks` entry not already known,
  `runtime.addTask(id, role, tier, deps)` and add its `TaskSpec` (with instruction + verify) to `this.specs`,
  then `continue` (the CEO dispatches it on a later step). Placed after `advance`, before `dispatch`. Guards
  against re-adding an existing id via `this.specs.has`.
- `test/orchestrator.test.ts` (add one): a scripted CEO does dispatch → **add_task (adds "b" deps ["a"])** →
  advance → dispatch → complete; assert `b` was added mid-run, ran, went green, and the run completed.

## Done criteria
`npm test` green (163 → 166); existing CEO/orchestrator tests unchanged; no new deps.

## Out of scope (follow-ups)
`split` / `replace` / `invalidate` a task; **repair→replan** (on repair exhaustion, diagnose → the CEO replans);
letting a real planner regenerate a sub-DAG. This increment is the `add_task` primitive they all build on.
