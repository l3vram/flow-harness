# Plan v0.13 — wire the planner into flow-run (objective → plan → gate → execute)

Self-contained execution plan. Cold context assumed.

**Repo:** `/Volumes/ExtSSD/mac-storage/projects/flow-harness` — git, npm workspaces, TS ESM
`NodeNext` (explicit `.js` import specifiers), `strict` + `noUncheckedIndexedAccess`, Node 22.

**Goal:** let `flow-run` take an OBJECTIVE (not a hand-written task list). It runs `@flow/planner`
to produce a spec + task DAG, prints it, and — because the tasks and their verify commands are
LLM-generated — **stops at a human gate by default**. Only with `acceptPlan: true` (the human has
reviewed) does it execute. Each planned task carries its own `verify`.

## Part 1 — per-task verify (executor + orchestrator)

### `packages/executor/src/types.ts`
Add `verifyCommand?: string[]` to `ExecContext`.

### `packages/executor/src/executor.ts`
In `run`, use the per-call override when present:
`const verify = runVerify(ctx.targetDir, ctx.verifyCommand ?? this.opts.verifyCommand ?? []);`
(Replace the current `runVerify(ctx.targetDir, this.opts.verifyCommand ?? [])` — a `verifyCommand`
passed in `ctx` wins.) Nothing else changes; security (path validation, containment) is untouched.
Add one test in `test/executor.test.ts`: a run passing `ctx.verifyCommand` uses it (e.g. a failing
command → blocked) over the constructor's.

### `packages/orchestrator/src/types.ts`
Add `verify?: string[]` to `TaskSpec`. Add `acceptPlan?: boolean` to `RunConfig` and make `tasks`
optional (`tasks?: TaskSpec[]`).

### `packages/orchestrator/src/orchestrator.ts`
When calling `this.executor.run(...)`, pass the task's verify:
`{ targetDir: this.opts.targetDir, context: ..., verifyCommand: spec.verify }` (in BOTH the first
attempt and the repair-loop retry). If `spec.verify` is undefined the executor falls back to its
own default, so existing behaviour is preserved.

## Part 2 — the planner gate in the CLI

### `packages/orchestrator/package.json` + `tsconfig.json`
Add dependency `"@flow/planner": "*"` and a tsconfig reference `{ "path": "../planner" }`.

### `packages/orchestrator/src/cli.ts`
Import `Planner` from `@flow/planner` and `TaskSpec` (already imported). After parsing the config and
BEFORE registering tasks, branch on whether tasks were provided:

- If `config.tasks` is a non-empty array → behave exactly as today (register them, run).
- Else if `config.objective` is set → **plan first**:
  ```
  const planner = new Planner(routerFromEnv());
  const plan = await planner.plan(config.objective, /* no repo context for v1 */ undefined);
  console.error("=== SPEC ===");           // print to stderr so stdout stays the report/plan JSON
  console.error(JSON.stringify(plan.spec, null, 2));
  console.error("=== TASKS ===");
  console.error(JSON.stringify(plan.tasks, null, 2));
  if (plan.spec.clarifications.length > 0 && config.acceptPlan !== true) {
    console.error("=== CLARIFICATIONS (resolve, then re-run with acceptPlan:true) ===");
    console.error(plan.spec.clarifications.map((c) => "- " + c).join("\n"));
    process.exit(2);
  }
  if (config.acceptPlan !== true) {
    console.error("Plan ready. Review it, then re-run with \"acceptPlan\": true to execute.");
    process.exit(2);
  }
  // acceptPlan === true: use the planned tasks
  const plannedSpecs: TaskSpec[] = plan.tasks.map((t) => ({
    id: t.id, role: t.role, tier: t.tier, deps: t.deps, instruction: t.instruction, verify: t.verify,
  }));
  // register these instead of config.tasks
  ```
  Register `plannedSpecs` into the runtime + specs map exactly as the existing loop does for
  `config.tasks`. (Refactor the existing task-registration loop to run over whichever list applies.)
- Else (no tasks and no objective) → stderr `flow-run: config needs either tasks or an objective`
  and exit 1.

The rest of the CLI (gates, lesson recording, `console.log(report)`) is unchanged. Note: use the
run-level `config.verifyCommand` for the `Executor` constructor as today (it remains the fallback);
per-task `verify` from the plan takes precedence via Part 1.
