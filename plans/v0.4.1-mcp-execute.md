# Plan v0.4.1 — `flow_execute` MCP tool (execution over MCP)

Self-contained execution plan. Cold context assumed.

**Repo:** `/Volumes/ExtSSD/mac-storage/projects/flow-harness` — git, npm workspaces, TS ESM
`NodeNext` (explicit `.js` import specifiers), `strict` + `noUncheckedIndexedAccess`, Node 22.

**Goal:** the MCP server currently exposes runtime management only (`flow_start`, `flow_add_task`,
`flow_plan`, `flow_ready`, `flow_set`, `flow_advance`, `flow_gate`, `flow_budget`, `flow_status`,
`flow_report`) — nothing runs the executor. Add **`flow_execute`** so an MCP host can run one task
through the executor (model writes files → applied under a target dir → verify → status set),
making the harness buildable over MCP, not just the CLI.

**Study first:** `packages/mcp-server/src/{tools.ts,server.ts,index.ts}`,
`packages/executor/src/{executor.ts,index.ts}` (the `Executor` class and `ExecResult`),
`packages/llm/src/index.ts` (`ModelRouter`, `routerFromEnv`, `FakeProvider`).

## Changes (touch ONLY `packages/mcp-server` + its tests)

### `packages/mcp-server/src/tools.ts`
1. Import: `import { Executor } from "@flow/executor";` and
   `import { routerFromEnv, type ModelRouter } from "@flow/llm";`.
2. Extend `ToolContext` with an optional injected router (for tests; production falls back to env):
   ```
   export interface ToolContext { baseDir: string; router?: ModelRouter; }
   ```
3. Allow async handlers: change the `ToolDef.handler` type to
   `(ctx: ToolContext, args: Args) => unknown | Promise<unknown>`.
4. Add a small optional-string-array reader next to the existing arg helpers:
   ```
   function optStrArray(args: Args, key: string): string[] {
     const v = args[key];
     if (v === undefined || v === null) return [];
     if (!Array.isArray(v) || v.some((x) => typeof x !== "string")) throw new Error(`'${key}' must be an array of strings`);
     return v as string[];
   }
   ```
5. Append this tool to the `tools` array:
   - `name`: `"flow_execute"`.
   - `description`: "Run one task through the executor: the model writes the files, they are applied
     under targetDir only, the configured verify command runs, and the task is set green (verify ok)
     or blocked. Requires a real LLM backend via FLOW_LLM_* env."
   - `inputSchema`: object with properties `runId` (string), `taskId` (string), `instruction`
     (string), `targetDir` (string), `verifyCommand` (array of string), `tier` (string); required
     `["runId","taskId","instruction","targetDir"]`, `additionalProperties: false`.
   - `handler` (async): use the existing `open(ctx, args)` helper to get the run's `Runtime` (it
     validates the run exists). Then:
     ```
     const taskId = reqStr(args, "taskId");
     const instruction = reqStr(args, "instruction");
     const targetDir = reqStr(args, "targetDir");
     const verifyCommand = optStrArray(args, "verifyCommand");
     const tier = optStr(args, "tier");
     const router = ctx.router ?? routerFromEnv();
     const executor = new Executor(router, { verifyCommand, tier });
     rt.setStatus(taskId, "running");
     const result = await executor.run({ id: taskId, instruction }, { targetDir });
     const ok = result.verify.ok;
     rt.setStatus(taskId, ok ? "green" : "blocked", ok ? "" : "verify failed");
     return { taskId, status: ok ? "green" : "blocked", files: result.files, verify: result.verify, reason: result.reason };
     ```
   (`open`, `reqStr`, `optStr` already exist in tools.ts — reuse them. `open` returns the `Runtime`.)

### Tests — `packages/mcp-server/test/tools.test.ts` (add cases; keep existing ones)
Import `FakeProvider`, `ModelRouter` from `@flow/llm`. Build an injected router whose fake returns
a valid file block:
```
const provider = new FakeProvider({ responder: () => "<<<FILE out.txt>>>\nhi\n<<<END>>>\n<<<REASON>>> ok" });
const router = new ModelRouter(new Map([[provider.name, provider]]), [{ tier: "sonnet", provider: provider.name, model: "m" }], "sonnet");
```
Add tests (use a temp `baseDir` and a temp `targetDir`, and `ctx = { baseDir, router }`):
- **executes a task and sets it green:** `flow_start` + `flow_add_task` (id `t`) via their handlers,
  then `await getTool("flow_execute").handler(ctx, { runId, taskId: "t", instruction: "make out.txt", targetDir })`;
  assert the returned `status` is `"green"`, `files` is `["out.txt"]`, the file exists under
  `targetDir` with content `hi`, and `flow_status` shows task `t` green. (No `verifyCommand` ⇒ verify
  ran:false, ok:true.)
- **verify failure blocks the task:** same but pass `verifyCommand: ["node","-e","process.exit(1)"]`;
  assert `status` is `"blocked"` and `verify.ok` is false.
