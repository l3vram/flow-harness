# v0.27 — executor robustness: a parse failure routes to the repair loop (not a run abort) — self-built

The v0.26 auto-build surfaced it: a **parse** error ("executor returned no file blocks", from
`parseChanges`) still aborts the whole run. The v0.17 fix wrapped `applyChanges` and `router.complete`,
but not `parseChanges`. Close that last un-caught throw path so every executor failure degrades to a
repairable/blocked task instead of crashing the run.

## Change — `packages/executor/src/executor.ts`
Wrap the `parseChanges(res.text, …)` call in try/catch. On failure, return a failed verification
(`ran:true, ok:false, output: "parse failed: <message>"`, `files:[]`) — the same path apply and provider
failures already take — so the orchestrator's repair loop feeds it back (bounded by `maxRepairAttempts`) and
the model gets another chance to reply with file blocks.

## Tests
- `packages/executor/test/executor.test.ts` (+1): a model reply with **no file blocks** (prose only) →
  `executor.run` does NOT throw; returns `files:[]`, `verify.ok:false`, output contains `"parse failed"`.
- `packages/orchestrator/test/orchestrator.test.ts` (+1): **recovery end to end** — attempt 1 returns a
  no-file-blocks response (parse fails), the repair loop retries, attempt 2 writes a valid file that passes
  verify → task `green`, `attempts === 2`. (Mirrors the v0.17 apply-recovery test, so we can see the run
  recompose instead of aborting.)
