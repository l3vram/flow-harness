# v0.31 — expose the autonomous run over MCP (`flow_run`) + a runbook — self-built

MCP-readiness for driving feature-adds on an external repo (an Android app is the target): a single MCP tool
that runs the whole loop — planner (or explicit tasks) → CEO → executor → QA — on a `targetDir`, returning the
report. A host like opencode registers the MCP server and says "add feature X"; flow does it.

## New library entry point — `packages/orchestrator/src/run.ts`
`runFromConfig(config: RunConfig, opts?: { router?: ModelRouter; baseDir?: string }): Promise<RunReport>` —
a **lean** reusable runner (the CLI's `main` keeps its git-worktree + lesson recording; this parallel path is for
libraries/MCP). It: inits the runtime under `<baseDir>/runs/<runId>`; resolves tasks (explicit `tasks`, or
`objective` → `Planner` → **derive acceptance criteria** and attach to the final task); over a library boundary the
plan gate is a **throw** `"plan pending: set acceptPlan:true"` (not a `process.exit`); registers tasks + approved
gates; runs `Orchestrator` (with run-scoped evidence) and returns the report. Uses `opts.router` (so the MCP tool
passes its injected router and tests stay offline) else `routerFromEnv()`. All its imports are existing orchestrator
deps (ceo, executor, llm, planner, verify) — no new orchestrator deps. Exported from `src/index.ts`.

## New MCP tool — `packages/mcp-server`
- `package.json` + `tsconfig.json`: add `@flow/orchestrator` (its `node_modules` symlink already exists).
- `src/tools.ts`: `flow_run` — input `{ runId, targetDir (required), objective?, tasks?, verifyCommand?, maxSteps?,
  contextRoot?, acceptPlan?, deriveCriteria? }`; the handler builds a `RunConfig` and returns
  `runFromConfig(config, { router: ctx.router, baseDir: ctx.baseDir })`. Description notes it needs a real LLM backend
  (`FLOW_LLM_*`) and, for an objective, `acceptPlan:true`. Tool count 14 → 15.

## Runbook — `docs/using-flow-via-mcp.md` (new)
How to (1) build the harness, (2) register the stdio MCP server (`flow-mcp`) in a host, (3) point `flow_run` at an
external repo with real provider keys, (4) verify with **Gradle commands as QA criteria** for an Android app
(`./gradlew testDebugUnitTest`, lint), and (5) the current limits: **Android UI/device QA (Layer C) is not built**, so
logic/unit-testable features are verified but visual UI is not; run flow **locally** (not Docker) so the machine's
Android SDK is available for the Gradle verify.
